# Test Vamos

## 1. Introduction

This directory contains the test suite of vamos. The suite combines a set
of native Amiga programs and python test scripts. First the native Amiga
programs will be compiled by various cross-compilers (see below) into native
Amiga binaries. Then vamos will be run with these binaries and the output
of the test programs will be compared to output generated by the programs
run on a real Amiga system.

In `src` directory you will find the Amiga test programs. In `suite` you
find the associated Python test programs.

## 2. Setup

You will need the `pytest` module to run the tests. Use pip to install
the module:

```
sudo pip install pytest
```

## 3. Cross-Compiler Setup

amitools currently supports the following cross-compilers to create the
AmigaOS binaries:

  - *gcc*: gcc 6.5 with AmigaOS support
  - *vc*: [vbcc](http://sun.hasenbraten.de/vbcc/) and [vasm]()
  - *agcc*: gcc 4.x with AROS m68k support
  - *sc*: SAS C v6.52 Amiga version running in vamos (commercial)

### 3.1 amiga-gcc

Use Bebbo's GCC 6.5 port for Amiga: [amiga-gcc](https://codeberg.org/bebbo/amiga-gcc)

  - see build instructions there
  - make sure to add gcc in macOS
```
brew install gcc@12
```
  - my env script `cv-env` is:
```
export GCC_VERSION=12
export SHELL=$(brew --prefix)/bin/bash
export CC=gcc-${GCC_VERSION}
export CXX=g++-${GCC_VERSION}
export PREFIX=$PWD/install
export PATH=$(brew --prefix bison)/bin:$PATH
export BREW_PREFIX=$(brew --prefix)
export CFLAGS=-I${BREW_PREFIX}/include
export LDFLAGS=-L${BREW_PREFIX}/lib
```
  - my build script `cv-build` is:
```
source env
gmake branch mod=binutils branch=amiga-2.46
gmake branch mod=gcc branch=amiga16.2
gmake update
gmake clean
gmake drop-prefix
time ( gmake min -j3 | tee b.log )
```

  - add the bin directory to your PATH (also add to your shell startup)

```
> export PATH=/opt/m68k-amigaos/bin:$PATH
```

### 3.3 AROS

AROS now supports m68k directly and also provides a gcc 4.x based toolchain
to build m68k binaries

#### Prerequisites

  - MacOS
    - Install [Homebrew](http://brew.sh)
    - Install the following packets:

```
> brew install gawk gnu-sed netpbm
```

#### Build

  - create a user accessible installation directory

```
> sudo mkdir -p /opt/m68k-aros
> sudo chown $USER /opt/m68k-aros
```

  - run build and install

```
# prepare Python
> export PYTHON=$(pyenv which python) # if you use pyenv
> pip install mako meson pyyaml

> git clone http://repo.or.cz/AROS.git

> ../AROS/configure --target=amiga-m68k --with-aros-toolchain-install=$PWD/install

# on macOS use Homebrew's gmake as it is version 4.x
> gmake crosstools
```

If the host binutils build fails in bundled zlib with an `expected ')'` error
in macOS `stdio.h`, its old `zutil.h` may define `fdopen(fd,mode)` as `NULL`
when `TARGET_OS_MAC` is set. This macro then interferes with the system
`fdopen` declaration. In the generated host binutils source under
`AROS-build/bin/darwin-aarch64/Ports/host/binutils/binutils-*/zlib/zutil.h`,
find the `#if defined(MACOS) || defined(TARGET_OS_MAC)` block and change the
`#else` immediately before the `#ifndef fdopen` fallback to:

```c
#elif !defined(__APPLE__)
```

This keeps the fallback for non-Apple targets while allowing macOS to use its
system `fdopen`. Re-run `gmake crosstools` after the edit. Since this file is
generated in the build tree, apply the same change to the binutils source or
patch used by your AROS build if you need it to survive a clean/reconfigure.

  - add the bin directory to your PATH (also add to your shell startup)

```
> export PATH=$PWD/install/bin:$PATH
```

### 3.4 SAS C 6.52

This is no cross-compiler but the native Amiga compiler. You will need a
pre-installed directory tree from the Amiga installation to run it here
with vamos.

The `Makefile` in this directory contains a line *SASC_INSTALL_DIR* that
describes the location where the `sc` directory of the Amiga installation
can be found in the host file system. The default is `volumes/sc`.

## 4. Copyrighted test fixtures

Some tests need original, copyrighted AmigaOS binaries (currently the ARexx
runtime, see `arexx/README.md`, and the shell variants in `shell-seg/`, see
`shell-seg/README.md`). These files are **never committed**. Instead
they are listed in `blob_files.txt` and stored encrypted in
`blob.tar.zstd.enc`; the tests skip themselves when the files are absent.

The manifest `blob_files.txt` lists every such file (paths relative to this
`test/` directory, one per line, `#` comments allowed; a directory entry
includes everything below it). A file listed there must also be ignored by a
`.gitignore` so it can never be committed; the lint CI job enforces this with
`blob_check.sh`.

### Restoring the fixtures

The blob is encrypted with a passphrase that is kept in the CI secret
`BLOB_PASSPHRASE`. For how to create that secret in the GitHub repository see
the "Copyrighted test fixtures" section in the top-level
[README.md](../README.md). To restore the files locally (after cloning, or in
CI):

```
BLOB_PASSPHRASE=... test/blob_decode.sh
```

`blob_decode.sh` unpacks the archive into this `test/` directory, recreating
every path in the manifest.

### Regenerating the blob

After changing `blob_files.txt` or replacing a fixture on disk, rebuild the
blob with the same passphrase:

```
BLOB_PASSPHRASE=... test/blob_encode.sh
```

The script checks that every listed file exists and is not tracked by git, then
packs exactly those files (tar, paths relative to `test/`) with zstd and
AES-256. Commit the regenerated `blob.tar.zstd.enc`. Both scripts also prompt
for the passphrase if `BLOB_PASSPHRASE` is not set.

### Adding a new fixture

1. Populate the file locally (e.g. with an `extract-*.py` script).
2. Add its path to `blob_files.txt`.
3. Make sure a `.gitignore` ignores it (`blob_check.sh` will tell you).
4. Run `BLOB_PASSPHRASE=... test/blob_encode.sh` and commit the new blob.
